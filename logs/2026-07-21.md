### Loop 2 ✅ — Dometrain: "CQRS architecture" (cap. 7) — visto y consolidado
- **Curso:** Event Sourcing con Marten & .NET (Dometrain) · cap. 7.
- **CQS:** comando = solo cambia estado (no devuelve resultados); query = solo lee (no cambia estado).
- **CQRS:** dos APIs separadas (command / query), cada una con su **modelo optimizado**; el dato viaja del command site al query site vía **eventos**.
- **Projections:** consumen eventos y llenan tablas optimizadas para lectura; corren **en aislamiento**; una projection nueva puede **reproducir todo el histórico**.
- **ES + CQRS:** eventos = modelo de persistencia **y** de comunicación (idénticos) → menos complejidad.
- **Estimación doble:** complejidad de projection ≈ nº de tipos de eventos fuente; comandos + projections = feature medible por adelantado.
- **Validación (≈2.7/3):** comando vs query ✅; ruta del dato vía eventos + projection ✅. Matiz corregido: distinguir **replay del aggregate** (reconstruir una entidad) de **backfill de una projection nueva** (reproducir el histórico completo en un read model que no existía cuando ocurrieron los eventos) — esto último es lo que habilita que persistencia = comunicación, imposible con CRUD que levanta eventos aparte.

### Loop 4 ✅ — Dometrain: "Introduction to our domain" (cap. 9) — visto y consolidado — inicio sección de código
- **Curso:** Event Sourcing con Marten & .NET (Dometrain) · cap. 9.
- **Dominio: BeerSender** (historia real — envío de cervezas belgas en lockdown 2022, UPS bloquea por licencia de alcohol, reenvío por PostNL). La app cubre "la parte divertida": llenar y rastrear cajas hasta enviarlas.
- **Naming (pet peeve):** se llama **BeerSender**, no "BeerSender.net" — el usuario no necesita saber con qué se construyó.
- **Primer aggregate = Box.** Commands (post-its azules del event storm): **Create box** (6/12/24 espacios) · **Add beer bottles** · **Apply shipping label** · **Close box** · **Ship box**.
- **Clave ES:** algunas operaciones pueden **fallar** según el **estado del aggregate** → un mismo command emite **eventos distintos** (éxito vs fallo).
- **Duda resuelta (failure event):** `public record ShippingLabelFailedToAdd(FailReason Reason)` con `enum FailReason { TrackingCodeInvalid }` anidado. `record` = evento inmutable + igualdad por valor; **enum anidado** = catálogo de razones **propio y aislado** del evento → evita colisiones con otros fallos (`BoxFailedToClose.FailReason`, etc.) y modela un solo evento de fallo que lleva el *por qué* como dato tipado (vs N eventos o excepción). Nota: dentro del record bastaba `FailReason Reason` (el tipo anidado ya está en scope).
- **Validación (2/2):** (1) un fallo se modela como **evento** —no excepción— para que quede persistido en la historia (auditable, replay, projections reaccionan); (2) no se reutiliza `FailReason` entre eventos porque cada uno tiene razones distintas.

### Loop 5 ✅ — Dometrain: "Value Types in commands & events" (cap. 10) — visto y consolidado
- **Curso:** Event Sourcing con Marten & .NET (Dometrain) · cap. 10.
- **Value type (DDD):** agrupar campos que se usan juntos (`ShippingLabel` = Carrier + TrackingCode) en un `record` (igualdad por valor); la **lógica viaja con el dato** (`IsValid`).
- **Strict vs Loose:**
  - **Strict** = lanza excepción en el constructor → imposible estado inválido, pero en **eventos** un breaking change **impide deserializar** los viejos → obliga a **versionar** value type + eventos. En **commands**: excepción **antes del dominio**.
  - **Loose** = no lanza, valida con métodos (`IsValid`) → **siempre deserializa** (red de seguridad), añades lógica sin versionar; sacrificio: puede representar estado inválido. En **commands**: el dominio sí puede manejar lo inválido.
- **Elección de Boyne:** loose en todo el curso. Otras estrategias válidas: strict + versionar; o primitivos en commands/events y value types solo en domain.
- **`BoxCapacity`** (record int Spots): factory estático mapea desired spots → 6/12/24; agrupa lógica + dato; usado en evento `BoxCreated`.
- **Duda resuelta (factory de `BoxCapacity`):** ¿quién llama a `BoxCapacity.Create(...)`? El **domain code / command handler** en el paso **execute**, transformando el `int DesiredNumberOfSpots` del command en un `BoxCapacity` válido (6/12/24) que se persiste en el evento `BoxCreated`. El command lleva la intención cruda; la regla de negocio la aplica el dominio, no el comando.
- **Validación (1.5/2 — ⚠️ punto a fijar):** P1 ✅ (el command refleja la solicitud, la regla 6/12/24 la aplica el dominio). **P2 ⚠️ INVERTIDA:** con value types **loose** un evento viejo **siempre deserializa** (no lanza) → NO hay que versionar; lo que *obliga a versionar* es **strict** (el constructor lanza al deserializar un valor ya inválido). Mnemotecnia: loose = siempre deserializa (red de seguridad, elección de Boyne); strict = puede romper → versionar.
